How I'd explain LUMIN in 28 minutes

This is a script for narrating LUMIN out loud in a system-design interview: state the requirements, trace one real request end to end, then land on the architecture diagram so it reads as "the thing I just traced" instead of an abstract box chart. From there it drills into the one decision everything else hangs off, then each subsystem, then LLD, gaps, and cost.

Subject: LLM-powered natural-language data analyst (FastAPI + LangGraph + React) Scope: backend workflow & data layer are the focus; frontend covered at the component/state level, not pixel-by-pixel Style: point-by-point, diagrams inline
00

How to run this in the room

0:00–0:02

Say the one-liner first, state the constraints that shape every later decision, then point at the architecture diagram early — it's the map I keep returning to.

  • One-liner: LUMIN lets a user upload a spreadsheet, point at a live SQL database, or drop a PDF, then ask questions about it in plain English — the backend turns the question into a SQL query (or a hybrid document retrieval), runs it, and returns both a written answer and a chart recommendation, streamed back token-by-node as it's produced.
  • Constraints that shape this: single developer, Groq as the primary (free-tier-friendly, fast-inference) LLM provider, Docker Compose on one host, Postgres/pgvector as the only datastore — so every design choice below is "what's the simplest thing that's still correct," not "what scales to a million users."
  • I'll volunteer gaps as I go rather than wait to be caught: there's no automated test suite to speak of, no query-level authorization check on cross-user data access, and the SQL-generation step trusts the LLM's output enough that injection is a real, named risk — I'll get to each of those in place, not gloss over them.
Why lead with the trace

An architecture diagram shown cold is just boxes and arrows. Walking one concrete question through the system first means the diagram in Section 3 lands as recognition, not new information — that's the order this doc follows too.

01

Requirements

0:02–0:04

Functional scope first, then the non-functional constraints that later decisions get justified against.

Functional

  • Connect a data source: upload a CSV/Excel file, point at a live SQL connection string, or upload a PDF/text document.
  • Ask a question in plain English about one data source, get back a natural-language answer plus, when appropriate, a chart (bar/line/pie/scatter/horizontal-bar) with the data pre-shaped for it.
  • Ask a question that spans multiple connected sources at once (e.g. "join my uploaded marketing CSV against the orders table in my Postgres DB") and get one federated answer.
  • Chat conversationally when the question isn't about the data at all, and let that same conversational turn create/update/list/delete lightweight "tasks" (a personal todo list that can optionally reference a dataset).
  • Persist conversations and replay history; manage data sources (list, delete, get AI-suggested starter questions, run an automated "data health" check).
  • Basic email/password auth with JWT sessions.

Non-functional

ConstraintWhat it actually means here
Low latency to first tokenResponses stream as newline-delimited JSON (NDJSON) per LangGraph node, not as one blocking call — the user sees "parsing question" before the SQL even exists.
Provider-agnostic LLM layerGroq, OpenAI, HuggingFace, and Ollama are all wireable through one small factory class; only Groq is exercised end-to-end today.
Single-tenant-per-request isolationEvery table a user creates gets a UUID-suffixed name and a data_sources row scoped to user_id — but see the known gap in §5 on how far that isolation actually reaches.
Cheap to runNo dedicated vector index infra beyond pgvector-in-Postgres; DuckDB is used in-process, on demand, rather than standing up a separate OLAP service.
Extensible query surfaceNew data source types (NoSQL, more document formats) should slot in without rewriting the LangGraph — the workflow is schema-driven, not source-type-driven.
02

A worked use case

0:04–0:07

One concrete request, traced end to end, before the architecture diagram — so the diagram reads as "oh, that's the thing I just traced."

A user has already uploaded sales_q3.csv (now table sales_q3_a1b2c3d4 in Postgres) and asks: "What were total sales by region last quarter?" — the same shape of question the project's own demo uses against the Brazilian E-commerce (Olist) dataset loaded into SQLite/Postgres per README.md's data-loading script.

  1. Frontend sends the questionsrc/hooks/useChat.ts → POST /api/chat/v1/ask-question/:id — a JWT-authenticated request carrying the question text, the conversation id, and the selected dataset_id.
  2. Controller resolves the data source and starts a streamchat_controller.py → ask_question() — looks up the DataSources row, saves the user's message, and (since exactly one source is selected) calls execute_workflow().
  3. Schema is introspected fresh, every calldb_config.py → DB.get_schemas() — SQLAlchemy's inspector reads live column names/types for sales_q3_a1b2c3d4. No cached schema means no staleness bugs, at the cost of one extra round trip per question.
  4. The LangGraph runs, streaming each node's outputsql_workflow.py → WorkflowManager.create_workflow() — parse question → generate SQL → validate/fix SQL → execute → (format answer & choose visualization in parallel) → format chart data. Each node's return value is yielded to the client the instant it's produced.
  5. SQL executes against the source tablesql_workflow.py → run_sql_query() — SELECT region, SUM(total) FROM "sales_q3_a1b2c3d4" WHERE ... GROUP BY region, cleaned of markdown fencing and backticks first.
  6. Two LLM calls run off the same resultsql_agent.py → format_results / choose_visualization — one turns rows into a one-sentence answer with the key number bolded, the other recommends a chart type and reasons about why.
  7. The whole exchange is persisted as one assistant messagechat_utils.py → save_message() — every streamed node's JSON is concatenated into Messages.content once the stream completes, so history replay can reconstruct the full step-by-step trace, not just the final answer.
  8. Frontend renders progressivelysrc/pages/chat.tsx, src/components/steps/* — a "steps" UI shows relevant tables, the generated SQL, and finally the chart component, as each NDJSON line arrives.
Why stream per-node, not per-token

Token-level streaming would need a proxy into the LLM provider's own stream for every node, multiplied across 5+ LLM calls in one question. Streaming the LangGraph's own node boundaries is coarser but far simpler, and it still gives the frontend the "show your work" UX (relevant tables → SQL → results → chart) that matters more here than raw typing-effect speed.

Why one Postgres for everything

App metadata, uploaded tabular data, and vector embeddings (via pgvector) all live in the same Postgres instance. That's one connection pool, one backup story, and one docker-compose service — the right call at this scale. It also means uploaded user data and system metadata share a database (not just a server), which is the seed of the tenancy gap called out in §5.

Folder layout

0:10–0:12

The architecture diagram made walkable — being able to point at "where's X handled" and land on one directory every time is itself a design signal.

backend/app/

  • api/routes → api/controllers → thin, request-shaped orchestration only
  • api/db/* — one SQLAlchemy Table definition per domain object (users, data_sources, chat_history, tasks)
  • api/validators — Pydantic request schemas, one file per feature
  • api/middleware — JWT auth middleware
  • langgraph/agents — SQLAgent, TaskAgent: the LLM-calling classes
  • langgraph/workflows — WorkflowManager: wires agent methods into a StateGraph
  • langgraph/prompt_templates — every prompt, kept out of agent logic
  • config — DB/VectorDB (data access), LLM (provider factory), env, logging
  • utils — the actual per-feature glue (chat_utils.py, task_utils.py) that controllers delegate to

src/ (frontend)

  • pages/* — one route each (chat, dataSource, chatHistory, todos, settings, auth)
  • zustand/stores — client state (chats, datasets, tasks, user)
  • zustand/apis — one axios wrapper module per backend resource
  • hooks/* — React Query mutations/queries wrapping the api modules

The backend follows a consistent Route → Controller → Utils/Agent → DB layering; every controller function has the same try/except/return-JSONResponse shape. That repetition is a little verbose, but it means an interviewer (or a new contributor) can predict the shape of any endpoint before opening it — a real, if unglamorous, design property.

NoSQL databases are explicitly out of scope today — the entire schema-introspection path (DB.get_schemas) leans on SQLAlchemy's relational inspector, which has no equivalent for a schema-less document store. Adding Mongo-style sources would mean a genuinely different code path, not a config flag.

05

The core bet: a fixed LangGraph, not an autonomous agent

0:12–0:15

The one decision every other subsystem hangs off — worth real weight since it's the most-probed thing in an actual interview.

The problem: turning "what were total sales by region last quarter?" into a correct, safe SQL query and a sensible chart needs several LLM-assisted steps (understand intent → write SQL → validate SQL → decide how to visualize), and those steps have a natural dependency order.

What LUMIN does: instead of giving one LLM a SQL-execution tool and letting it decide, in a loop, what to call next (the "autonomous ReAct agent" pattern), LUMIN hard-codes the step order as a LangGraph StateGraph — parse_question → generate_sql → validate_and_fix_sql → execute_sql → {format_results, choose_visualization} → format_data_for_visualization — with exactly one true branch point (should_continue, which routes irrelevant questions to a conversational reply instead of SQL generation).

flowchart TD
    Start([START]) --> ParseQuestion[Parse Question]
    ParseQuestion --> ShouldContinue{is_relevant?}
    ShouldContinue -->|Yes| GenSQL[Generate SQL Query]
    GenSQL --> ValidateSQL[Validate and Fix SQL]
    ValidateSQL --> ExecuteSQL[Execute SQL Query]
    ExecuteSQL --> FormatResults[Format Results]
    ExecuteSQL --> ChooseViz[Choose Visualization]
    ChooseViz --> FormatViz[Format Data for Visualization]
    ShouldContinue -->|No| ConvResponse[Conversational Response]
    FormatResults --> End([END])
    FormatViz --> End
    ConvResponse --> End
Why a fixed graph over a tool-calling agent

An autonomous agent gives the model freedom to re-plan, retry, or call tools in a different order — powerful, but non-deterministic and harder to stream meaningfully (you don't know what node is "next" until the model decides). A fixed graph gives up that flexibility in exchange for: predictable per-step streaming (the frontend's step-by-step UI depends on this), a validate-and-fix step that's guaranteed to run before every execution, and a much smaller prompt-injection surface, since the LLM never chooses which tool to invoke next — it only ever fills in the next node's expected output shape. The tradeoff accepted: if a question genuinely needs a variable number of steps (e.g. "try three different groupings and tell me which is most interesting"), this graph can't do that without a redesign.

Known gap

"Validate and fix SQL" is itself an LLM call asked to judge and rewrite SQL from the same model family that generated it — there's no independent, non-LLM guard (e.g. an EXPLAIN-based dry run, or a SQL parser allow-listing statement types) between generation and execution. A sufficiently adversarial prompt could still produce a destructive statement that both generation and "validation" agree looks fine.

Federated multi-source joins

When a question is asked against more than one selected data source, execute_multi_source_workflow() builds a combined schema and a source_map (table name → connection URL, or the literal string "system") and passes it into the same LangGraph. The graph doesn't know or care that it's multi-source — the branching happens one layer down, inside run_sql_query(): it string-matches which table names from source_map appear in the generated SQL, and if more than one distinct source is involved, it pulls each table into a Pandas DataFrame and registers it with an in-memory DuckDB connection, then runs the (Postgres-flavored) generated SQL against DuckDB instead.

Why DuckDB instead of a real federation layer

Standing up a federated query engine (Trino/Presto) for a project this size would be pure overkill. DuckDB embeds as a library, accepts Pandas DataFrames directly via zero-copy registration, and speaks enough SQL to run the LLM-generated query unmodified. The tradeoff: every join fetches full tables into memory first — there's no pushdown, no partial-fetch, so this only works while tables stay small.

Known gap — tenant isolation

Table names are matched by a case-insensitive substring check against the raw SQL string (table.lower() in cleaned_query.lower()), not a parsed AST — a table name that happens to be a substring of another identifier could misroute. More importantly, nothing in run_sql_query re-checks that the requesting user actually owns every table implicated by the LLM's SQL; source-of-truth ownership is only checked once, when the data sources were originally selected in the controller.

The SQL agent loop — what each LLM call actually sees

0:18–0:20

Every node in the graph is one LLM call with a fixed prompt template and a fixed output parser — documenting the actual I/O shape, since that's what makes the graph deterministic.

NodeInputOutput shapeParser
parse_questionschema + question{is_relevant, relevant_tables[]}JSON
generate_sqlschema + question + parsed_questionraw SQL string, or literal NOT_ENOUGH_INFOplain string
validate_and_fix_sqlschema + sql_query{valid, issues, corrected_query}JSON
format_resultsquestion + query_result rowsone sentence, key number in **bold**plain string
choose_visualizationquestion + sql_query + query_result{recommended_visualization, reason}JSON
format_data_for_visualizationquestion + query_result + chart typechart-type-specific JSON (a different prompt per chart type, see graph_prompts.py)JSON
Why structured JSON over parsing free text

Every node that needs anything beyond plain prose asks for strict JSON and runs it through LangChain's JsonOutputParser. That's a real, if soft, contract: it lets downstream nodes trust field names instead of regexing an LLM's prose. It's soft because Groq's LangChain integration here isn't using guaranteed structured-output/tool-calling mode — the prompts just instruct "no backticks, no code fences, valid JSON only" and hope the model complies, which is why clean_sql_query() still exists to strip markdown fences defensively.

Known gap

None of the six prompts are few-shot-verified against the actual target LLM's JSON reliability at scale — a malformed JSON response from any JSON-parsed node raises an uncaught parser exception that bubbles up as a generic 500, not a graceful "let me try again" retry.

08

Hybrid search for documents (RAG)

0:20–0:22

The document-chat path is a separate, simpler pipeline from the SQL one — no LangGraph, just LangChain's RetrievalQA with an ensemble retriever.

  • Chunking: 750-char chunks, 50-char overlap, split on newlines (reader_utils.py).
  • Retrieval is hybrid, not pure-vector: a semantic retriever (pgvector similarity, k=2) is combined with a BM25 keyword retriever (also k=2, built by pulling every chunk for that collection back out of Postgres and indexing it in-memory) via LangChain's EnsembleRetriever, weighted 50/50.
  • Why hybrid at all: pure semantic search misses exact-match lookups — a product SKU, an exact name — because embeddings cluster on meaning, not surface form. BM25 catches the literal string; the vector retriever catches paraphrase and concept-level questions. The ensemble's reciprocal-rank fusion means either retriever surfacing a chunk near the top is usually enough to get it into the final context.
  • Why k=2 per retriever, not more: this is a direct application of the "lost in the middle" effect — Liu et al. (2023) show LLMs attend far more reliably to information near the start or end of the context window than to the same information buried mid-context, so a small, well-ranked context set (4 chunks max, post-fusion) tends to beat a large noisy one for a "stuff"-chain prompt that concatenates everything into one call.
Known gap

get_all_documents() re-fetches and re-indexes the entire collection into a fresh in-memory BM25 index on every single question — there's no caching of the BM25 index across turns in a conversation, so a large document collection means real, repeated latency and memory cost per message.

What's done well

The BM25 import is wrapped in a try/except that falls back cleanly to vector-only retrieval if the optional dependency isn't available — the document-chat path degrades gracefully instead of hard-failing.

09

Tasks, auth & the frontend shell

0:22–0:23

Three smaller pieces, covered together since none needs its own diagram.

Tasks — a second, cheaper agent

Task requests ("add a task to review the outliers") route through a separate TaskAgent, not the SQL graph. It's a keyword pre-filter (task, todo, remind, …) gating one single LLM call that returns an intent + action + structured task fields; CRUD then happens with plain SQLAlchemy, no further LLM involvement. This is a deliberate two-tier design: cheap, fast, deterministic routing before ever paying for an LLM call.

Auth

Email/password with passlib hashing and a JWT (HS256, one shared SECRET_KEY) carrying only {id}. AuthMiddleware runs before every request except an explicit path allowlist (/, /docs, login, signup), decodes the token, and stashes user_id on request.state.

Known gap

JWTs never expire meaningfully in practice (no refresh flow, no visible short TTL in create_access_token beyond whatever PyJWT default applies), and there's no token revocation/blacklist — a leaked token is valid until it naturally expires.

Frontend shell

Zustand holds client state (chats, datasets, tasks, user) with no persistence middleware beyond what localstorageUtils.ts does manually for the auth token. React Query wraps every mutation for retry/loading/error state. Streaming responses are read via axios's responseType: 'stream' + onDownloadProgress, parsed as NDJSON client-side (parseData() in utils.ts) — a slightly unusual choice since the Fetch API's native ReadableStream is the more common way to consume SSE-shaped output, but it keeps every network call going through the same axios client and its auth-header injection.

Naming the architecture

0:23–0:24

11

LLD & best practices

0:24–0:25

Zooming from architecture into the classes, schemas, and conventions an LLD round would actually probe.

Core classes

WorkflowManager

  • Owns the compiled StateGraph and the shared DB handle
  • run_sql_query() also does row serialization (Decimal→float, datetime→ISO string, bytes→utf-8) so JSON encoding downstream never has to think about SQLAlchemy row types

SQLAgent

  • Every method does the same explicit required_keys check against state before touching it — a manual substitute for a validated state schema at each boundary
  • Each method builds a fresh prompt | llm | parser LangChain Expression Language chain per call rather than caching them — simple, slightly wasteful, never the bottleneck here

AgentState (TypedDict)

  • Two fields (answer, visualization) are declared Annotated[str, operator.add] — LangGraph's reducer mechanism, so if two branches both wrote to the same key the graph concatenates rather than overwrites; used here mainly for the parallel format_results/choose_visualization fan-out

DB / VectorDB

  • DB is instantiated per-connection-string, not pooled/cached across requests — a new engine per external url-type source, every query
  • VectorDB lazily initializes the embedding model once per process (module-level singleton pattern via if self._embedding is None)

Conventions actually followed

  • Every controller function: try / except HTTPException / except SQLAlchemyError / except Exception, each returning a uniform create_response(status_code, message, data) envelope — consistent, if repetitive enough that a shared decorator would remove real duplication.
  • DB sessions are always opened via with db.session() as session: so commit/close happens deterministically, even on exceptions.
  • Prompts live entirely in prompt_templates/, never inlined in agent methods — keeps the "what does the model actually see" question answerable by reading one file per prompt.
If asked: why TypedDict instead of a Pydantic model for AgentState? — a real tradeoff, not an oversight
  • LangGraph's StateGraph works natively with TypedDicts and merges partial dict returns from each node automatically — a Pydantic model would need either full-object reconstruction per node or a compatibility shim.
  • The cost: no runtime validation on state transitions — a node that returns a wrongly-typed value fails downstream, not at the point of the mistake.
12

Observability

0:25–0:26

What's actually logged today, and the honest gaps — no smoothing this over.

  • logging_config.py sets up coloredlogs at DEBUG globally (with a comment noting it should drop to INFO in production — it hasn't been changed) and every module gets its own named logger via get_logger(__name__).
  • Several hot paths (run_sql_query, DB.execute_query, the auth middleware's token check) still use bare print() for debug output alongside the real logger — leftover from active development, not yet cleaned up.
  • LangChain/LangSmith tracing is wired in (LANGCHAIN_PROJECT env var is read and set) but explicitly disabled: LANGCHAIN_TRACING_V2 = "false" is hard-coded in env.py, so there is no per-run trace of prompts/completions/latencies today even though the plumbing exists to turn it on.
Known gap

No request-id/correlation-id threading through a request's logs, no structured (JSON) logging, no metrics (latency histograms, LLM token counts, error rates) exported anywhere. Debugging a production incident today means grepping logs.txt for nearby timestamps.

Future work: scaling, cost & evals

0:27–0:27

What's not needed at today's actual scale, but naming what would change and why is what's being checked for here.

Cost, with real numbers

LUMIN's primary provider is Groq. As of the pricing checked for this doc (self-serve tier, per the Groq/Helicone pricing pages):

Model (used in code today)InputOutput
llama-3.1-8b-instant$0.05 / 1M tokens$0.08 / 1M tokens
llama-3.3-70b-versatile$0.59 / 1M tokens$0.79 / 1M tokens

A single "ask a question" turn against one data source makes 4–5 LLM calls (parse, generate SQL, validate, format results, choose viz, format viz data) — at a few hundred tokens each, that's low-single-digit-cents even on the larger model. The real cost driver at scale would be volume of turns, not per-turn token count.

Source, dated

Groq self-serve pricing checked September 2026 via Helicone's Groq pricing calculators and Groq's own published rate card. Note: several Groq models (including both used here) reportedly moved to enterprise "contact sales" pricing in late August 2026 per third-party trackers — worth re-verifying current self-serve availability before quoting these numbers as current.

Scaling — not needed today, but here's what would change

  • DuckDB federation fetches full tables into memory. Fine at demo scale (Olist dataset, low-millions of rows); breaks down once any joined table doesn't fit in the API process's RAM. Fix: push filter/aggregation predicates down before the fetch, or cap fetched row counts.
  • One FastAPI process, no worker pool declared in the Dockerfile's dev command. Uvicorn's default single-worker mode means concurrent streaming requests share one event loop — fine for async I/O-bound LLM calls, but CPU-bound work (pandas joins, BM25 indexing) would block other requests. Multiple Uvicorn workers behind a load balancer is the obvious next step.
  • No caching layer. Schema introspection and BM25 index-building both re-run from scratch on every single question. A Redis-backed schema cache (invalidated on data source upload/delete) and a per-collection BM25 index cache would cut the most repeated work.

Evals — the honest gap

Not yet done

There is no evaluation harness — no held-out set of (question, expected SQL or expected answer) pairs, no automated check that a prompt change didn't regress SQL-generation accuracy. backend/app/tests/ exists but covers DB config and one SQL-agent unit test, not end-to-end correctness. Given LangSmith tracing is already wired (just disabled), the natural next step is turning tracing on and building a small golden-question eval set against it before iterating further on prompts.

Deployment

0:27–0:28

What actually ships today vs. the concrete next step past one developer's laptop.

  • Today: docker-compose.yml — three services (backend, frontend, ankane/pgvector Postgres image), backend runs uvicorn --reload with the source bind-mounted, frontend runs npm run dev. This is explicitly a dev-mode compose file, not a production one (hot-reload flags, no build-and-serve step for the frontend, hard-coded default DB credentials).

Tradeoffs & what I'd change next

0:28–0:28

Closing section, in the interviewer's own words: strengths, weaknesses, and the one thing I'd fix first.

If I had to pick one thing to fix first

SQL execution safety. Right now, "validate and fix" is an LLM call from the same family that generated the query — not an independent guard. I'd add a real allow-list layer between generation and execution: parse the generated SQL with sqlglot or similar, reject anything that isn't a SELECT against tables the requesting user actually owns (cross-checked against data_sources, not just string-matched against source_map), and only then hand it to the LLM-based "fix" step for genuine syntax repair.

Strengths

  • The fixed-graph design for SQL generation is the right call for streaming UX and predictability, and it's applied consistently.
  • Hybrid retrieval (BM25 + vector) for documents is a genuinely good, well-justified choice, not cargo-culted.
  • Clean provider-agnostic LLM factory and a consistent controller error-handling shape make the codebase predictable to extend.
  • DuckDB-based federation solves a real, non-trivial "join across two live sources" problem with minimal added infrastructure.

Weaknesses

  • SQL execution trusts the LLM more than it should (§5, §6).
  • No cross-request caching (schema, BM25 index) means repeated, avoidable latency on every single question.
  • No eval harness, despite tracing infra already being present but switched off.
  • Migrations (Alembic) are a dependency, not a working system yet — schema changes are manual today.

Glossary

LangGraph
The state-machine orchestration library LUMIN uses to wire the SQL agent's steps into a StateGraph with explicit nodes and edges — this project uses it for a fixed pipeline, not an autonomous agent loop.
AgentState
The TypedDict shared across every LangGraph node in sql_workflow.py; each node returns a partial dict that LangGraph merges into it, using reducers (operator.add) for the fields two branches might both write.
Hybrid search
Combining BM25 (keyword/exact-match) retrieval with dense vector (semantic) retrieval via an EnsembleRetriever, used for LUMIN's document-chat path so exact identifiers aren't lost to pure semantic search.
Lost in the middle
The empirical finding (Liu et al., 2023) that LLMs attend more reliably to context near the start/end of a prompt than to the same information buried mid-context — the reason LUMIN's retrievers are capped at k=2 each rather than stuffing in more chunks.
pgvector
The Postgres extension used as LUMIN's only vector store — document embeddings live in the same database as every other table, via LangChain's PGVector integration.
DuckDB federation
LUMIN's approach to multi-source joins: pull each involved table into a Pandas DataFrame, register it with an in-memory DuckDB connection, and run the LLM-generated SQL there instead of against either source database directly.
source_map
The dict built per multi-source question mapping each involved table name to its origin (a connection URL, or the literal string "system" for the app's own Postgres) — how run_sql_query decides whether a question needs federation.
NDJSON streaming
LUMIN streams each LangGraph node's output as one JSON object per line over StreamingResponse, rather than token-level streaming from the LLM itself — coarser, but matches the frontend's step-by-step "show your work" UI.
Strategy pattern (LLM factory)
The LLM class in llm_config.py — callers get back a BaseLLM-compatible object regardless of whether .groq(), .openai(), or .ollama() was called, so the rest of the codebase never branches on provider.
